# 002 — Someone else's record returns 404, not 403

**Status:** accepted

## Context

If customer A asks for customer B's order, the obvious answer is `403
Forbidden` — "this exists, but it is not yours."

That answer leaks. Order references are short and sequential, so an attacker
can walk the range and sort the responses: `403` means a real order,
`404` means an empty slot. They learn how many orders the store has taken and
which references are live, without ever seeing one.

## Decision

An authorisation miss on someone else's object returns **404**, with the same
body as a genuinely missing record. The two cases are indistinguishable from
outside.

This is done by scoping the queryset to the current user before fetching, so
the row is simply not found rather than found-and-refused.

## Consequences

- The reference space cannot be probed.
- Permission failures on *admin* routes still return 403. That is a different
  question — "you are not staff" says nothing about whether a particular record
  exists — and the code keeps them separate: `config/exceptions.py` converts
  Django's `PermissionDenied` to 404, while DRF's permission classes return 403
  as normal.
- Debugging is slightly harder: a genuine bug and an authorisation problem look
  the same in the response. The server log distinguishes them.

## Where it lives

`config/exceptions.py`, plus the per-view querysets in `apps/orders/views.py`
and `apps/accounts/views.py`.
