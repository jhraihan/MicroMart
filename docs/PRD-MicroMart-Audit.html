1Executive Summary

What MicroMart is, the state it is in, and the three things worth fixing first.

MicroMart is a single-vendor electronics e-commerce web application for the Bangladesh market: a React storefront and a role-gated admin dashboard over a Django REST API, with a 117-product catalogue, PC-builder compatibility engine, coupon engine, review moderation and Cash-on-Delivery checkout.

Verdict

The codebase is materially better than typical for a project of this scope. The architecture is disciplined and the hard problems — the ones most implementations get wrong — are correct. This audit found no defect in the order state machine, the inventory ledger, the payment verification path, or the money arithmetic.

What it did find is a narrower and more specific class of problem: a security control that is configured but not active, a user-facing statement that contradicts the code, and several safety nets that were never installed. None of these require re-architecting anything.

Framing Every item in this document is an addition to working code, not a correction of a flawed design. No finding proposes rewriting the services layer, the order state machine, or the payments module. Those are the parts of this project worth defending.

The three that matter most

IDFindingWhy it leads
F2+F3 Rate limiting is inert Throttle rates are tuned and written, but DEFAULT_THROTTLE_CLASSES is never set, so DRF applies none of them. The codebase reads as protected. Compounded by an unconfigured cache, which would make counters per-worker even once enabled. This is the only finding rated critical.
F1 The UI contradicts a security property The account page tells users that changing their password does not sign them out elsewhere. The backend does exactly that, and a passing test pins it. A user who suspects their account is compromised is being told the safe action will not work.
F12 3,249 lines of tests never run A 13-spec Playwright suite, including a 1,030-line accessibility spec, exists and is excluded from CI. The work is already paid for; only the wiring is missing. Highest value per unit of effort in this document.

What is not in question

Verified directly against the source during this audit and found correct:

  • Oversell prevention — SELECT ... FOR UPDATE taken in primary-key order, stock re-checked inside the lock, backed by a database CHECK (stock >= 0) constraint.
  • Payment verification — the IPN handler takes the order reference from the gateway's validation response, never from the notification body, so a forged payload cannot aim a genuine small payment at a large order. The browser callback reads and writes nothing.
  • Object-level authorisation — a miss returns 404, never 403, so the identifier space is not confirmed. Admin permission classes still correctly return 403, because the handler catches Django's PermissionDenied rather than DRF's.
  • Money — DECIMAL(12,2) throughout, serialised as decimal strings, never floats.
  • Order snapshotting — product name, variant label, SKU, unit price, shipping address and tax rate are copied onto the order, so later catalogue edits cannot rewrite history.
  • Single source of business logic — the storefront and admin surfaces call the same service functions, so rules cannot drift between them.

4.1 P0 — Correctness and security

P0

F1 · The UI states the opposite of a security property

frontend/src/features/account/ChangePasswordPage.jsx:100 (and comment at :16) · backend/apps/accounts/services/auth.py:221 · docs/HANDOFF.md §4

The account page displays: "changing your password here does not yet sign you out on other devices." This was true once. It is not true now — change_password() calls revoke_all_sessions(user), which blacklists every outstanding refresh token, and the behaviour is pinned by test_changing_the_password_invalidates_every_existing_refresh_token.

Impact. This is not a cosmetic defect. Someone changes a password precisely when they believe their account is compromised, and this note tells them the action will not evict the intruder. It may push a user toward a worse decision at the worst possible moment. The security work was done correctly and is being disclaimed.

Fix

Replace the note with the truth, and state it as a feature rather than a footnote:

For your security, changing your password signs you out on all
other devices. You will stay signed in here.

Also update the misleading comment block at :16, and mark docs/HANDOFF.md §4 RESOLVED in the style that file already uses. Consider surfacing "Signed out on all other devices" in the success message.

P0

F2 · Global rate limiting is configured but inert

backend/config/settings/base.py:118–138

REST_FRAMEWORK defines DEFAULT_THROTTLE_RATES with anon: 120/min and user: 300/min. It never defines DEFAULT_THROTTLE_CLASSES. In DRF, rates without classes are inert — see the runtime evidence in §2.4.

Impact. Only five views throttle anything, all via explicit ScopedRateThrottle. Everything else is unlimited: product list, search suggest, checkout quote, order placement, cart mutation, wishlist, PC-builder, and every admin CRUD endpoint. The danger is not merely the absent limit — it is that the tuned rates make the codebase read as protected, and a passing single-process login-throttle test reinforces that impression.

Fix 
"DEFAULT_THROTTLE_CLASSES": (
    "rest_framework.throttling.AnonRateThrottle",
    "rest_framework.throttling.UserRateThrottle",
),

Must ship in the same change as F3. Add a regression test that calls an endpoint with no explicit throttle — GET /api/v1/products/ — 121 times and asserts 429. That test fails today; passing it is the proof the fix is real.

P0

F3 · No cache backend, so throttle counters would be per-worker

backend/config/settings/base.py — no CACHES key

With CACHES undefined, Django falls back to LocMemCache (confirmed at runtime). DRF stores throttle counters in the default cache. Under Gunicorn with N workers, a 10/min limit becomes an effective 10×N/min, and counters reset whenever a worker recycles.

Impact. Fixing F2 without this yields throttling that is real in tests and porous in production — arguably worse than none, because it would be trusted.

Fix 
CACHES = {"default": env.cache("CACHE_URL", default="locmemcache://")}

django-environ already provides env.cache() — no new parsing dependency. In prod.py, fail fast if the backend is still LocMem, matching the existing guard style used for the SameSite/CORS pairing. Redis or Django's DatabaseCache are both acceptable; see §8 on the trade-off.

P0

F4 · No error boundary anywhere in the React tree

frontend/src/main.jsx · frontend/src/routes/index.jsx

A repository-wide search for ErrorBoundary, componentDidCatch, getDerivedStateFromError and errorElement returns zero matches. React Router v7 is in use and its per-route errorElement is available and unused.

Impact. Any render-phase throw unmounts the entire tree: the user gets a blank white page with no message and no recovery path. A single unexpected null from the API turns one broken panel into a total blackout. Chunk-load failures after a deploy — a long-lived tab requesting a hashed asset that no longer exists — fail the same way.

Fix

Two layers. A per-route errorElement on the top-level storefront and admin route objects rendering a new src/pages/ErrorPage.jsx that uses useRouteError() — this keeps the layout chrome so the user can navigate away. Plus one class ErrorBoundary wrapping <App /> in main.jsx as the outermost net. Style it to match the existing NotFoundPage so it reads as intentional.

P0

F5 · No frontend unit test layer exists

frontend/package.json — no runner, no test script, 0 test files under src/

No Vitest, Jest, or Testing Library appears in dependencies, even transitively. The contrast with 1,009 backend tests is the single most visible asymmetry in the repository.

Impact. Pure, high-risk modules have no coverage: lib/money.js (BDT formatting — a rounding bug here is a financial bug, and its symbol substitution depends on ICU behaviour that varies by Node version), the four Zod schema files including the Bangladesh phone regex, the four Zustand stores, and checkout/paymentReturn.js on the money path.

Fix

Add vitest, @vitest/coverage-v8, @testing-library/react, @testing-library/user-event, jsdom. Configure inside the existing vite.config.js so the @ alias is reused and no second config file appears. Test in this order: money.js → Zod schemas → stores → paymentReturn.js. Record the resulting coverage number in the README; the delta from zero is itself the artifact.

4.2 P1 — Unthrottled endpoints

These follow from F2 and should be fixed alongside it. Each needs a deliberate scope rather than a blanket rate.

P1

F6 · Token refresh is unauthenticated, unthrottled, and writes a row per call

backend/apps/accounts/views.py:75

RefreshView is AllowAny with no throttle, and every call performs a database write (token.blacklist()) plus a user lookup — an unauthenticated write-amplification vector.

Fix — give it its own scope, not auth 
# base.py DEFAULT_THROTTLE_RATES
"refresh": "60/min",

# apps/accounts/views.py
throttle_classes = [ScopedRateThrottle]
throttle_scope = "refresh"

It must not share the auth scope: App.jsx refreshes on every full page load, so sharing the login budget would break normal browsing. Note that config/settings/dev.py:23–42 currently claims refresh does share that scope — it has no scope at all. Correct that comment as part of this change (F21).

P1

F7 · Email verification is unthrottled

backend/apps/accounts/views.py:129

VerifyEmailView accepts a raw token and performs an indexed lookup with no rate limit. Tokens are secrets.token_urlsafe(32), so this is a database-load concern, not a token-guessing one — the search space is not brute-forceable, and the fix comment should say so rather than overclaim.

Fix

Apply the existing auth scope (10/min). A user clicks a verification link once, perhaps twice.

P1

F8 · Checkout quote is an unthrottled coupon-enumeration oracle

backend/apps/orders/views.py:45 (quote), :70 (placement)

CheckoutQuoteView is AllowAny and unthrottled, and returns distinguishable COUPON_* codes — an attacker can enumerate the coupon namespace at line rate and learn precisely why each code failed. Order placement is likewise unthrottled, permitting inventory-exhausting and table-flooding submissions.

Do not flatten the error codes Distinguishable codes (COUPON_EXPIRED vs COUPON_MIN_ORDER_NOT_MET) are a genuine UX asset that the storefront branches on. Degrading the error contract would be a regression. The correct mitigation is rate limiting plus a purpose-built endpoint.
Fix 
# base.py DEFAULT_THROTTLE_RATES
"checkout":    "30/min",   # chattier than a page view: district + coupon edits
"place_order": "10/min",   # a shopper places one order

# OrderListCreateView — mirror the existing get_permissions() pattern
def get_throttles(self):
    if self.request.method == "POST":
        return [ScopedRateThrottle()]
    return super().get_throttles()

Then add POST /api/v1/coupons/validate/ in the empty promotions/urls.py stub (F23), delegating to the existing coupon service. This gives checkout a cheap purpose-built call and lets the coupon question be throttled independently of the pricing question.

4.3 P1 — Operational gaps

P1

F9 · No observability of any kind

backend/config/ — no health route, no error tracking, no request correlation

Absent: error tracking (Sentry or equivalent), health/readiness endpoints, structured logging, request IDs, metrics. Logging is a plain StreamHandler with a human-readable format. Outside the payments module — which has good logging discipline — the codebase logs nothing at all.

Fix

Add apps/common/health.py with a split liveness/readiness pair mounted at the root (/healthz/, /readyz/), not under /api/v1/ — these are infrastructure, not versioned API. Liveness must never fail for an external reason, or an orchestrator will restart a healthy app because the database blinked; readiness checks database and cache reachability and returns 503 when degraded.

Add a RequestIDMiddleware that honours or generates X-Request-ID, echoes it in the response, and exposes it to logging — then feed it into the F10 logger so a 500 in the log can be matched to the exact response a user saw. Sentry last, guarded on SENTRY_DSN with send_default_pii=False.

P1

F10 · Unhandled 500s leave no structured record

backend/config/exceptions.py — no logger imported

The custom exception handler has no logging. Unhandled exceptions reach Django's default logger with no view context and no correlation id; with DEBUG=False the client gets an opaque 500 and there is no other record.

Fix — log in one branch only 
response = drf_exception_handler(exc, context)
if response is None:
    logger.exception("Unhandled exception in %s %s (view=%s)", ...)
    return None

Placement is load-bearing. response is None is precisely the "DRF could not turn this into an HTTP error" path — the true 500. Logging at the Http404 or DomainError branches would flood the log with ordinary traffic, since this application's 404-not-403 design makes authorisation misses routine.

P1

F11 · Outbound SMTP has no timeout

backend/config/settings/base.py:194–201 · backend/apps/accounts/services/auth.py:136–160

EMAIL_TIMEOUT is unset (verified None), so smtplib inherits the OS socket default — potentially minutes. request_password_reset additionally sends inline, while register_user correctly defers via transaction.on_commit. fail_silently=True prevents an error but does not prevent the block.

Impact. An unreachable-but-not-refusing mail host pins a Gunicorn worker per request. The endpoint is AllowAny, so this is cheap to trigger.

Fix 
EMAIL_TIMEOUT = env.int("EMAIL_TIMEOUT", default=10)
The obvious second half is a no-op Moving the send into transaction.on_commit changes nothing on its own: request_password_reset is not wrapped in @transaction.atomic (verified), and outside an atomic block on_commit executes its callback immediately. EMAIL_TIMEOUT is the fix that actually bounds worker blocking. Deferral is cosmetic symmetry unless atomicity is added too.
P1

F12 · A substantial test suite never runs

.github/workflows/ci.yml:80–105 — frontend job runs lint and build only

The repository contains 3,249 lines across 13 Playwright specs — browse, guest checkout, signed-in checkout, cart merge, six admin specs, and a 1,030-line accessibility spec covering axe rules, keyboard operation, touch targets and focus traps. None of it executes in CI. The Playwright config even reads process.env.CI, implying an intent that was never wired up.

Impact. The most impressive artifact in the repository is invisible, and regressions in accessibility or the checkout path are caught by nothing.

Fix

Add a third CI job reusing the mysql:8.4 service block from the backend job: install both stacks, migrate, seed_demo, start Django and the Vite preview, then npx playwright test. Cache ~/.cache/ms-playwright, upload the HTML report on failure, and set retries: 2. Run it non-blocking for a week before making it required. Sequencing: this needs the dev-environment throttle relaxation from F2 first, or the whole suite will 429.

P1

F13 · CI is asymmetric and has no quality gate

.github/workflows/ci.yml

The frontend job lints; the backend job does not. Neither measures coverage. There is no dependency audit, no Dependabot configuration, no security scanning, and the lint step lacks --max-warnings=0 so its 24 warnings can never fail a build.

Fix

Add pytest-cov with --cov=apps --cov=config; add ruff (which replaces flake8, isort and black-check in one binary, and whose S ruleset covers what Bandit would report without the noise); add pip-audit and npm audit as non-blocking steps. Measure the baseline before setting a gate, then set --cov-fail-under just below it — an aspirational gate is one you disable within a week.

4.4 P2 — Quality and polish

P2

F14 · No machine-readable API contract

backend/requirements/ — no drf-spectacular or drf-yasg

Four hand-written contract documents exist in docs/ and are genuinely good — but they are prose that can drift from the code, and there is no generated schema, no /schema/ and no browsable docs route for roughly 50 endpoints across two consuming surfaces.

Fix

Add drf-spectacular; mount Swagger UI at /api/docs/. Budget effort for three known friction points: the custom error envelope needs declaring once as a component; OrderListCreateView has method-dependent serializers and permissions; and ProductListView injects facets into the paginated response, which introspection cannot see. Add a CI step running spectacular --fail-on-warn so the schema cannot rot.

P2

F15 · Shared links preview blank

frontend/index.html:3–15 · frontend/src/lib/seo.js

The HTML shell carries a title, theme colour and icons but no description, no og:*, no twitter:*. All meta is injected client-side. Facebook, WhatsApp and most non-Google crawlers do not execute JavaScript.

Impact. For a Bangladeshi storefront, WhatsApp and Facebook sharing is a primary distribution channel, and every shared link currently renders as a bare URL. It also affects this project directly: a demo link pasted to a recruiter previews as nothing.

Fix

Add static description, og:title, og:description, og:image (absolute URL, 1200×630), og:type, og:url and twitter:card to index.html. Keep seo.js for per-page overrides — the static tags are the floor, not a replacement. Document the limitation honestly: per-product previews still need SSR or prerendering, which is out of scope. A reviewer respects a stated limitation more than an overclaim.

P2

F16 · Two competing validation idioms

9 forms use Zod + React Hook Form; 8+ hand-roll useState

Hand-rolled forms include AddressesPage (a full Bangladesh address form with no field validation), ProfilePage, ChangePasswordPage, ForgotPasswordPage, AdminTaxonomyPage and ImageManager (file upload with no client-side type or size check).

A second UI lie, in the same file as F1: ChangePasswordPage tells the user the password must mix "letters and numbers" and enforces only minLength={8}.

Fix — reuse, do not rewrite

features/checkout/schemas.js already contains a validated Bangladesh address and phone schema. AddressesPage should import it. That is the refactor's headline: one address schema serving both checkout and account. Requires F5 (Vitest) first — write the schema tests, then refactor against them. Preserve ForgotPasswordPage's deliberate error handling (see §5.2).

P2

F17 · A failed fetch is indistinguishable from an empty result

frontend/src/features/account/AccountOverviewPage.jsx, AddressesPage.jsx, builder/SharedBuildPage.jsx

These destructure query data with a default (const { data: addresses = [] }) and never branch on isError. A 500 therefore renders the "No addresses saved yet" empty state — actively misleading.

Fix — the default is not the bug

Keep = []; it correctly prevents .map crashes. The defect is the missing isError branch. AdminTaxonomyPage.jsx:59 already does this correctly and is the in-repo template: destructure isError, error and refetch, render an error state with retry, and fall through to the empty state only on a successful zero-row response. Do the two account pages first — they sit on the checkout-adjacent path.

P2

F18 · Sitemap is an uncapped, uncached full-table scan

backend/apps/catalog/seo_views.py:96–140

The view iterates every listable product and builds the whole XML document in memory, with no 50,000-URL cap (the sitemaps.org limit, beyond which crawlers reject the document) and no server-side caching. The Cache-Control header it sets is a client directive that does nothing for the database.

Fix

Wrap in @cache_page(3600) — available once F3 lands, and a visible payoff from that work — and cap the product queryset at 50,000. Do not add a throttle: a cached response is cheap, and throttling this URL would rate-limit Googlebot, which is actively harmful.

P2

F19 · The ignore rule will silently eat any env example

frontend/.gitignore:34 — .env* with no negation

The root .gitignore correctly negates !.env.example; the frontend one does not. A committed frontend/.env.example would be silently ignored. Three VITE_* variables are undocumented and discoverable only by grep: VITE_API_BASE_URL, VITE_BACKEND_ORIGIN, VITE_SHOW_DEMO_CREDENTIALS.

Fix — order matters

Add !.env.example to frontend/.gitignore before writing the file, or the commit will appear to succeed and contain nothing. Then add frontend/.env.example documenting all three variables, with an explicit warning on the demo-credentials flag. Verify with git check-ignore -v frontend/.env.example.

P2

F20 · The documented architecture exists nowhere

CLAUDE.md:109–118 vs. the repository contents

Project documentation describes an Nginx (TLS, static, reverse proxy) → Gunicorn → MySQL topology. A repository-wide search for Dockerfile, docker-compose, nginx.conf, gunicorn.conf, Procfile and IaC returns exactly one artifact: frontend/vercel.json, which describes a static-host deployment — a different topology altogether.

Fix

Build the missing artifacts (see §7 item 2), then either remove vercel.json or document it explicitly as the alternate static-host path. Keeping both without explanation is the confusing state. Add a CI job that runs docker compose up -d, curls /readyz/, and tears down — an unexercised Compose file rots within a month and is worse than none.

P2

F21 · Documentation contradicts the code it describes

docs/HANDOFF.md §1 · config/api_urls.py:26 · apps/promotions/admin_urls.py:14 · config/settings/dev.py:23–42

Four separate false statements, all confidently phrased:

  • HANDOFF.md §1 lists payments, promotions, reviews and dashboard as having "no endpoints and no business logic". Payments has 3 routes and a 681-line service; reviews has 4; dashboard has 7.
  • Two comments describe dashboard/urls.py as "still an empty stub". It has 7 routes.
  • dev.py asserts that refresh "shares the auth scope with login", which is the stated justification for relaxing that rate to 2000/min. Refresh has no scope at all.

Impact. This codebase's character is load-bearing comments that explain why. That is a real strength — but a reviewer who catches one confidently false comment discounts all of them.

Fix

Correct all four. For the two "empty stub" comments, keep the reasoning (endpoints live in the app owning the model) and drop only the false premise. Rewrite the dev.py block after F6 gives refresh a real scope.

P2

F22 · The README lists shipped features as "future improvements"

README.md:591–606

The section lists wishlist functionality, product reviews and ratings, advanced filtering and search, and a CI/CD pipeline as potential future work. All four are built, routed and tested — wishlist and reviews are confirmed at apps/reviews/urls.py:22 with 80 tests, and CI has been running since the workflow was added.

P2

F23 · An empty URL module is still mounted

backend/apps/promotions/urls.py — urlpatterns = [], included at config/api_urls.py:16

Harmless at runtime, but it is a live import of a file with no content.

Fix

Rather than deleting it, fill it — this is the natural home for the POST /coupons/validate/ endpoint that resolves the F8 enumeration oracle. It is already mounted, so no wiring change is needed.

5Assessed — No Action

Five items that look like defects, were examined, and are being left alone. Recording them matters: an audit that cannot distinguish deliberate design from oversight is not worth acting on.

5.1 The demo-credentials flag is a feature, not a leak

VITE_SHOW_DEMO_CREDENTIALS renders working demo logins on the login page. It is off by default and requires an exact 'true' opt-in at build time. A 28-line comment records that it was deliberately loosened from import.meta.env.DEV — because that stricter gate makes a public demo impossible to build — and spells out exactly what the admin row grants.

Verdict: no change. The dangerous state is the one you must ask for. Document the flag in frontend/.env.example (F19) with a warning and move on. Listing this as a defect would flag one of the codebase's best-documented decisions as a mistake.

5.2 The swallowed error in the password-reset flow is correct

ForgotPasswordPage catches and discards errors from the reset request, then always shows the neutral "if an account exists" screen. This is not sloppiness: distinguishing failure modes is precisely the user-enumeration leak the flow exists to prevent, and it matches the backend, which deliberately returns None for unknown addresses and always responds 204.

Verdict: at most a narrow refinement. One could report transport failure — the request never reached the server, which reveals nothing about the email — while keeping every HTTP response neutral. That is a subtler change than "stop swallowing errors", and the current behaviour is defensible as-is.

5.3 Upload limits are not unset in the dangerous sense

Django defaults DATA_UPLOAD_MAX_MEMORY_SIZE and FILE_UPLOAD_MAX_MEMORY_SIZE to 2.5 MB. "Not configured" here means "not narrowed from a safe default", not "unbounded". The application already enforces a 5 MB image cap in its admin service, and those endpoints are admin-gated.

Verdict: minor tightening only. The genuinely useful addition is DATA_UPLOAD_MAX_NUMBER_FIELDS, which bounds hash-collision-style POST floods. Ranking this beside a real hole would dilute the credibility of the register.

5.4 Coupon error codes must stay distinguishable

Covered under F8. Flattening COUPON_EXPIRED and COUPON_MIN_ORDER_NOT_MET into a generic failure would degrade a working error contract that the storefront branches on. Rate limiting is the right control.

5.5 The default-destructure idiom is good practice

Covered under F17. const { data = [] } prevents crashes and should stay; the missing isError branch is the defect. Framing it as "remove the default" would produce a worse codebase.

8Risks & Trade-offs

Where a fix can make things worse, and what to decide deliberately rather than by accident.

8.1 Enabling throttling will break the end-to-end suite

Playwright drives a real browser from one IP address, and catalogue-heavy specs will exhaust anon: 120/min in seconds. Relax anon and user in dev.py — following the precedent already set for AUTH_THROTTLE_RATE — in the same change as F2, and before wiring e2e into CI. Sequenced naively, Phase 1 and Phase 2 will appear to break each other.

8.2 A shared cache contradicts a documented decision

Project documentation states that no Redis is used in v1. That deferral was about background job queues, so adding a cache is defensible — but it must be stated, not silently reversed. A reviewer who reads the decision and then finds Redis in a Compose file will notice. Amend the line and write ADR-007 accordingly.

Django's DatabaseCache remains a legitimate alternative that adds no new service, is genuinely adequate at this scale, and — honestly — would make for a more interesting ADR than the one defending Redis.

8.3 Caching facet counts can make the application wrong

Facet counts include in_stock figures that change with every order. Caching them can show "In stock (3)" when the true figure is zero. At 117 products the performance benefit is theoretical. If done at all, sequence it last, derive the cache key from the parsed query rather than the raw query string (so equivalent filter orderings share a key), and document the staleness explicitly. This is the one proposed change that can introduce user-visible inaccuracy.

8.4 A cross-origin demo will log users out in Safari

Hosting the SPA and the API on different registrable domains forces SameSite=None on the refresh cookie — which is a third-party cookie, blocked by default in Safari and Firefox. The demo would exhibit apparently random logouts, on the most visible artifact of the project. The production settings file already warns about this and names the fix: serve the SPA from a subdomain of the API's own domain.

8.5 Automation that nobody reads is worse than none

Dependabot on a solo project generates pull-request noise quickly. Use grouped updates and a low open-PR limit, or the resulting stale-PR graveyard will read worse than having no automation at all. The same applies to an unexercised Compose file (F20) and an aspirational coverage gate (F13).

9.2 Environment notes for the next developer

MySQL port
Documentation specifies 3307; the service on the review machine listens on 3306. Reconcile DATABASE_URL before running the suite.
No .env in a clone
backend/.env is correctly gitignored, so a fresh checkout has no settings. Copy backend/.env.example first — DJANGO_SECRET_KEY has no default and Django will not start without it.
SQLite is not an option
Migration catalog/0003 issues CREATE FULLTEXT INDEX. The suite is MySQL-bound by design.
Test database
The ecom grant must cover test_ecom.* as well, or pytest cannot create its database.
Parallel runs
One shared test schema: concurrent pytest processes contend. Deadlocks and "unknown database" errors during a run are contention, not defects.
